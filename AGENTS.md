# Project-wide instructions

- Read `PROJECT_CONTEXT.md` and the nearest applicable `AGENTS.md` before changing files.
- Read `PROJECT_PROFILE.json` when it exists. It is local, may contain personal data, and must remain ignored by Git.
- Discover repository skills under `.agents/skills/` lazily. For an ordinary task choose one primary workflow skill and add at most two supporting skills only when the current phase requires them; do not preload every potentially related skill.
- Prefer the smallest sufficient context. Do not load a supporting skill, source, tool capability report, build log, calculation record, or review record unless it is needed for the current decision. Reduce large tool output to compact JSON or a short summary before loading more context.
- When `PROJECT_CONTEXT.md` contains `setup_state: template` and the user wants to begin a real project, use `$setup-tul-project` before initializing or editing a document. Do not force onboarding for read-only questions.
- During onboarding, assume no prior Git, GitHub, LaTeX, or terminal experience unless the user demonstrates otherwise. Use plain language, explain jargon at the moment it becomes relevant, accept ordinary faculty and work-type names, and keep questions in small groups.
- Before initializing any TUL formal document, ask whether its generated declaration/title-page variant should be `male` or `female`. Keep exactly one active `\ThesisStart` command at all times; when the official IS STAG introductory PDF arrives, replace the generated variant with that PDF rather than adding a second command.
- Treat `templates/upstream/` as immutable vendor material. Never edit, compile, or use it as an expert/citable source.
- Work on the thesis only in `prace/`, on defense slides only in `obhajoba/`, and on expert sources only in `zdroje/`.
- Use `$matlab-to-tikz` when the current deliverable creates, converts, restyles, repairs, or inserts a MATLAB or numerical graph. Merely reading `.mat` data or noticing that a dataset could be plotted does not activate it.
- Load `$create-project-visuals` when a visual will actually be created, sourced, adapted, inserted, or specifically audited. During ordinary planning or prose review, a brief visual recommendation does not require loading the skill.
- Never add decorative academic visuals merely to fill space. For every used visual, preserve provenance, permissions, scientific meaning, a factual caption, and a stable cross-reference; clearly distinguish reproduced, adapted, original, and AI-generated material.
- For factual or citation-bearing work, search registered project sources first through `zdroje/INDEX_ZDROJU.md` and the page-level index. Verify the original page before citing; if support is missing, report the gap and recommend new evidence.
- Before creating or reviewing citations, read `zdroje/90_zpracovane/poznamky-a-souhrny/SRC-0003_SRC-0004_SRC-0005_citation-policy.md` and then apply any stricter faculty-specific rule recorded in `PROJECT_CONTEXT.md`.
- Register every independently compiled document and its entry point in `PROJECT_CONTEXT.md`. The primary thesis uses `prace/main.tex`; additional formal documents use `prace/dokumenty/<slug>/main.tex`.
- Prefer installed, task-appropriate tools; never install software, packages, fonts, or toolboxes without approval.
- Preserve user changes, avoid machine-specific absolute paths and secrets, and verify every material output.
- Use `$verify-scientific-calculations` for material scientific results that enter project evidence, figures, tables, arguments, or conclusions. Routine arithmetic, trivial unit conversions, and internal sanity checks do not require a `CALC-NNNN` record.
- Automatically use `$diagnose-tul-latex` for LaTeX environment and build failures. Project compile scripts and the XeLaTeX -> Biber -> MakeIndex -> XeLaTeX -> XeLaTeX sequence remain authoritative; optional plugins may diagnose but must not silently replace this workflow.
- Use `$review-agent-output` at an explicit review boundary: a requested review, a grouped handoff/checkpoint, a final-submission workflow, or a user's approval/rejection of a defined scope. Keep ordinary iterative edits marked `agent-draft` instead of creating a new `REV-NNNN` after each change. Technical checks never equal human approval.
- Treat Wolfram and LaTeX plugins as optional accelerators, never project requirements. Continue with reproducible local tools when they are unavailable. Do not send unpublished, personal, confidential, or otherwise sensitive project data to an external plugin without first telling the user what would be sent and receiving confirmation.
- Use `$final-submission-check` only for explicit final, submission, or preflight requests; use `$check-assignment-compliance` to compare existing work with an official assignment.
- Use `$review-supervisor-feedback` for external reviewer comments, `$review-thesis-chapter` for an academic audit of existing chapter text, and `$plan-thesis-structure` for prospective evidence-led outlines.
- Use `$prepare-defense` for defense content and narrative, `$tul-presentation` for its technical Beamer realization, and `$mock-defense` for an interactive evidence-grounded rehearsal.
- Use `$audit-figures-and-tables` for existing visual/table audits, `$terminology-consistency` for cross-document terminology, and `$privacy-publication-check` before public sharing.
- Route an installed executable through `$local-tool-router`; route an MCP, plugin, connector, or authorized external API through `$external-tool-router`. Discover only task-relevant capabilities and do not add another overlapping router.
- After first-time setup, summarize the created files and recommend a fresh focused chat with an exact opening prompt. Create a new chat only when the user explicitly asks.
- After initializing a primary thesis plus an experimental or practical supporting document, recommend two persistent focused chats over the same workspace: `MAIN – hlavní práce` for selective final prose and `EXPERIMENTY – praktický deník` for complete records. Offer `OTÁZKY A REŠERŠE` and later `OBHAJOBA` as optional chats. Explain that chats separate context but do not create separate repositories or duplicate files.
- Automatically use `$manage-experiments` for laboratory work, trials, measurements, samples, apparatus settings, failures, deviations, raw results, practical diaries, experiment IDs, and promotion of selected findings into the main thesis. Preserve the complete record; never rewrite the diary into a cleaner history after the fact.
